# 青少年体态筛查监控中心规范

## 0. 文档状态

- 版本：`v1.0`
- 状态：`Draft / 作为后续开发改进的主导规范`
- 适用范围：`Rehab-V3.1` 为主执行仓库，`v0.3.0-stable` 仅作为历史能力参考
- 目标：为产品定位调整、信息架构重构、数据模型演进、权限改造和后续功能开发提供统一依据

当本规范与历史产品叙事冲突时，以本规范为后续改造方向。
当本规范与当前运行代码冲突时，代码描述现状，本规范描述目标态。

## 1. 规范语言

本文使用以下关键词：

- `MUST`：必须满足，否则不视为符合本规范
- `SHOULD`：推荐满足，除非存在明确且记录在案的例外
- `MAY`：可选项，可按场景决定是否实现

## 2. 产品定位

### 2.1 目标定位

本产品的主定位 MUST 定义为：

> 面向学校、青训机构、体教融合场景的青少年体态筛查、风险分层、复测跟踪与监控协同平台。

### 2.2 非目标定位

以下方向在当前阶段 MUST NOT 作为主定位：

- 通用运动康复平台
- 医疗诊断平台
- 面向个人消费者的纯 C 端姿态 App
- 以治疗方案生成为核心卖点的系统

### 2.3 产品承诺边界

系统输出 SHOULD 表述为：

- 体态筛查结果
- 风险提示
- 趋势变化
- 复测建议
- 训练与康复建议

系统输出 MUST NOT 默认表述为：

- 医疗诊断结论
- 疾病确诊
- 替代医生判断的临床意见

## 3. 核心用户与角色

### 3.1 目标用户

- 机构管理员：负责机构、校区、班级、设备、账号和统计看板
- 筛查执行员：负责现场采集、拍摄、补录和提交筛查结果
- 复核人员：负责异常复核、风险确认、报告审核和复测建议
- 家长或监护人：查看学生筛查结果、复测建议和趋势变化
- 学生只读用户：在受控范围内查看个人历史结果

### 3.2 角色映射建议

当前角色体系 SHOULD 逐步映射为：

| 现有角色 | 目标角色 |
|---|---|
| `super_head_coach` | `org_admin` |
| `head_coach` | `reviewer` |
| `assistant_medic` | `screener` |
| `athlete_readonly` | `guardian_readonly` 或 `student_readonly` |

当前角色命名保留兼容层 MAY 存在，但新的业务文案 MUST 使用目标角色命名。

## 4. 产品原则

后续所有改造 SHOULD 遵守以下原则：

1. 筛查优先：优先服务“快速发现问题”而非“生成复杂治疗内容”
2. 监控优先：一次筛查只是起点，核心价值来自长期档案与复测闭环
3. 机构优先：组织、班级、批量任务、汇总看板优先于单人孤立流程
4. 现场优先：采集流程必须足够快，适合校内和训练场景使用
5. 风险分层优先：结果必须服务后续分层管理，而非只停留在展示
6. 隐私优先：未成年人数据与授权流程必须前置考虑
7. 可追溯优先：关键筛查、复核、导出、权限行为必须有审计记录

## 5. 领域模型

后续开发 MUST 围绕以下核心对象建模：

| 实体 | 说明 |
|---|---|
| `Organization` | 机构，如学校、青训中心、康复中心 |
| `Campus` | 校区或分部 |
| `Group` | 年级、班级、队伍、训练组 |
| `StudentProfile` | 学生档案 |
| `GuardianConsent` | 监护人授权记录 |
| `ScreeningTask` | 一次批量筛查任务 |
| `ScreeningSession` | 一名学生的一次筛查会话 |
| `CaptureArtifact` | 视频、截图、关键帧、标注数据 |
| `PostureObservation` | 筛查指标与异常观察项 |
| `RiskLevel` | 风险等级与分层标签 |
| `FollowUpAction` | 复测、干预、家长通知、转诊建议等动作 |
| `Report` | 个体或汇总报告 |
| `AuditLog` | 权限、导出、复核、状态变化记录 |

## 6. 信息架构

目标态信息架构 SHOULD 收敛为以下一级模块：

- `监控首页`
- `筛查工作台`
- `学生档案`
- `报告中心`
- `预警与复测`
- `机构管理`

### 6.1 监控首页

MUST 提供：

- 今日待筛查人数
- 已完成筛查人数
- 异常学生数量
- 待复测数量
- 机构总体趋势入口

### 6.2 筛查工作台

MUST 提供：

- 快速筛查入口
- 标准筛查入口
- 学生选择或扫码进入
- 现场拍摄与补录
- 会话完成状态

### 6.3 学生档案

MUST 提供：

- 基本信息
- 历次筛查记录
- 风险标签
- 趋势图
- 报告与附件
- 跟踪动作记录

### 6.4 报告中心

MUST 支持：

- 个人筛查报告
- 班级或队伍汇总报告
- 机构周期报告
- 可控导出

### 6.5 预警与复测

MUST 支持：

- 高风险学生列表
- 需复测学生列表
- 超期未复测提醒
- 多次异常趋势提醒

### 6.6 机构管理

MUST 支持：

- 组织结构
- 账号角色
- 数据授权状态
- 设备与站点
- 基础阈值配置

## 7. 核心功能要求

### 7.1 筛查模式

系统 MUST 保留两类模式：

- `快速筛查`：单视角、低时长、适合现场快检
- `标准筛查`：多视角、完整流程、适合建档与复评

未来如新增模式，MUST 说明其目标场景、时长、输出差异和替代关系。

### 7.2 风险分层

每次筛查结果 MUST 落到统一的风险分层结果，不得只给自由文本。

建议标准：

- `normal`
- `watch`
- `review`
- `high_risk`

每个等级 SHOULD 对应：

- 是否需要复测
- 是否需要人工复核
- 是否需要家长通知
- 是否建议转专业人员

### 7.3 报告输出

每份个人报告 MUST 包含：

- 学生身份信息
- 筛查时间与场景
- 采集模式
- 关键观察项
- 风险等级
- 复测或跟进建议
- 免责声明

每份报告 MUST 明确区分：

- 机器判定内容
- 人工复核内容
- 建议性内容

### 7.4 趋势与复测

系统 SHOULD 支持同一学生的纵向趋势对比。

趋势展示 MUST 以筛查周期和风险变化为主，不得仅展示零散图表。

### 7.5 批量机构场景

系统 MUST 支持机构级使用，而不是仅支持单人孤立使用。

后续迭代至少应覆盖：

- 班级或队伍批量筛查任务
- 学生名单导入
- 按组织汇总完成率
- 按组织汇总异常率

## 8. 前端改造规范

### 8.1 主应用壳

后续主应用 MUST 继续收敛在 `src/hub/` 下的统一壳层，不应再增加并行入口应用。

### 8.2 模块定位

现有模块建议调整为：

- `Vision3` -> 主筛查引擎
- `ROM` -> 辅助专项评估能力
- `MedVoice` -> 非主流程能力，降级为补充模块
- `Treatment Plan` -> 非首页主入口能力

### 8.3 页面文案

后续页面文案 MUST 优先使用以下术语：

- 筛查
- 监控
- 风险
- 复测
- 跟踪
- 机构
- 学生档案

以下术语 SHOULD 降级或仅限二级页面出现：

- 康复治疗
- 处方
- 病历
- 临床诊断

### 8.4 组件与流程

每个新页面或重构页面 SHOULD 明确对应以下之一：

- 筛查入口页
- 工作流页
- 档案页
- 报告页
- 看板页
- 配置页

不应继续扩大“单文件大页面”的复杂度。

## 9. 后端与 API 规范

### 9.1 认证与权限

服务端 MUST 采用后端真实鉴权。

以下行为 MUST NOT 继续作为目标态方案：

- 仅依赖 `localStorage` 角色切换
- 缺失鉴权时自动回落到高权限默认角色
- 仅前端做权限隐藏而后端不校验

### 9.2 API 领域划分

后续 API SHOULD 按领域拆分，而不是继续围绕单一分析接口堆叠：

- `/api/orgs/*`
- `/api/groups/*`
- `/api/students/*`
- `/api/screening-tasks/*`
- `/api/screening-sessions/*`
- `/api/reports/*`
- `/api/follow-ups/*`
- `/api/audit/*`

### 9.3 数据存储

生产形态 MUST NOT 依赖 JSON 文件作为主数据存储。

至少应满足：

- 并发安全
- 可查询
- 可审计
- 可按机构隔离
- 可按学生追踪历史记录

### 9.4 审计

以下操作 MUST 写审计日志：

- 登录
- 导出报告
- 修改风险等级
- 复核确认
- 删除或归档结果
- 权限变更

## 10. 数据与隐私规范

### 10.1 未成年人数据

青少年数据处理 MUST 默认视为高敏感业务。

系统 MUST 支持：

- 监护人授权状态记录
- 数据用途说明
- 机构归属隔离
- 导出可追踪
- 删除与归档策略

### 10.2 最小化原则

任何新字段或新采集能力都 SHOULD 说明：

- 为什么必须采集
- 用于哪个功能
- 保存多久
- 谁可以访问

### 10.3 文案约束

对家长或学生可见的文案 MUST 避免制造医疗恐慌。

推荐表达：

- 存在体态异常风险
- 建议复测
- 建议进一步观察或咨询专业人员

## 11. 非功能要求

### 11.1 性能

- 快速筛查流程 SHOULD 在低配置设备上保持可用
- 首次进入筛查工作台 MUST 优先保障拍摄和基础分析可用
- 大模型或重报告生成 MUST 不阻塞核心筛查流程

### 11.2 可用性

- 现场主操作 SHOULD 在 3 次点击内进入拍摄
- 快速筛查 SHOULD 支持最少必要输入
- 异常状态 MUST 有明确的重试与补录路径

### 11.3 可测试性

任何新增核心流程 SHOULD 同时补：

- 单元测试
- 关键交互测试
- 权限越权测试
- 报告快照或契约测试

### 11.4 可观测性

系统 SHOULD 至少观测：

- 筛查完成率
- 拍摄失败率
- 风险等级分布
- 复测完成率
- 报告导出次数

## 12. 交付优先级

### P0：方向收敛

- 完成产品命名与主叙事调整
- 明确机构、学生、筛查、复测四条主线
- 确定目标角色体系
- 停止新增与主定位无关的治疗型页面

### P1：MVP

- 筛查工作台
- 学生档案
- 个人筛查报告
- 风险分层
- 复测列表

### P2：机构化

- 学校/班级/队伍结构
- 批量筛查任务
- 机构汇总看板
- 家长通知与授权状态

### P3：增强

- 趋势监控
- 高风险预警
- 干预建议闭环
- 专项评估插件扩展

## 13. 不在当前阶段范围内

以下内容 MAY 保留探索，但 MUST NOT 阻塞主线：

- 泛病种扩展
- 重度依赖语音问诊的流程
- 复杂治疗方案自动生成
- 面向个人用户的社交或社区功能

## 14. 变更准入规则

从本规范发布后，任何中大型改动 SHOULD 在立项说明中回答以下问题：

1. 该改动服务于哪个目标用户？
2. 它属于筛查、监控、复测、报告、机构管理中的哪条主线？
3. 是否会新增或修改核心实体？
4. 是否涉及未成年人隐私、导出、授权或审计？
5. 是否会扩大旧的“康复治疗平台”叙事？
6. 需要同步更新哪些文档、测试和权限规则？

若无法回答以上问题，则该需求 SHOULD 暂缓进入开发。

## 15. 与现有代码的落地关系

当前建议的落地优先顺序：

1. 以 `Rehab-V3.1` 作为主改造仓库
2. 保留 `v0.3.0-stable` 作为历史参考，不再承载主线产品演进
3. 优先改造权限、数据模型、信息架构
4. 再重构筛查流程、学生档案、报告体系
5. 最后再决定哪些康复与训练建议能力保留为二级模块
